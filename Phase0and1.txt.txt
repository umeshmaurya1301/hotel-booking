0. Context for the implementer
You are building the domain core of a hotel booking platform — a Spring Boot backend for a machine-coding exercise. This phase produces no controllers, no persistence, no Spring wiring. It produces the domain model, value objects, the booking state machine, domain exceptions, and repository port interfaces, plus their unit tests.
Later phases (not yours) add: inventory materialisation and pricing, atomic reservation and locking, payment SPI and resilience, refunds and ledger, REST API, webhooks.

1.2 Version rationale — read before changing anything
Spring Boot 4.1.1 — Spring Boot 4.1.0 shipped 10 June 2026; 4.1.1 on 21 Aug 2026. Spring Boot 3.5 reached open-source end of life on 30 June 2026, so 4.1.x is the correct target for a new project. Boot 4.x is built on Spring Framework 7, requires Java 17 minimum, and supports up to Java 26 in 4.1.
Java 21, not 25 — deliberate. Java 25 is an LTS and would work, but it requires Gradle 9.1.0 or later, and 21 has the broadest toolchain and IDE support. Virtual threads (needed in Phase 4) have been stable since 21. Reviewer reproducibility outweighs newness: the build must work first try on someone else's machine.
Gradle — use whatever wrapper start.spring.io emits. Do not upgrade it.
Kotlin DSL — better IDE completion; no Kotlin code is written.

1.4 De-risking step — do this before writing any domain code

Does not resolve → report back immediately. The fallback is Spring Boot 3.5.16 (the final 3.x patch, 25 June 2026) with resilience4j-spring-boot3, which is well-trodden.
Twenty minutes spent proving the dependency graph now beats discovering a broken build at Phase 4. Do not skip this.

2.1 Typed identifiers
One record per ID. Purpose: make book(propertyId, roomTypeId) impossible to call with the arguments swapped.
public record BookingId(String value) { /* validate non-blank */ }

Create: OwnerId, PropertyGroupId, PropertyId, RoomTypeId, GuestId, BookingId, PaymentId, RefundId, LedgerEntryId, MsgId.
Requirements for each:
Compact constructor rejects null and blank with IllegalArgumentException.
static of(String) factory.
static newId() generating a UUID — except MsgId, which is always client-supplied and must have no generator.
toString() returns the raw value.
2.2 DateRange — build this first
Everything else depends on it.
public record DateRange(LocalDate checkIn, LocalDate checkOut)

Member
Contract
constructor
Rejects null. Rejects checkOut <= checkIn (a zero-night stay is invalid). Rejects a span exceeding MAX_STAY_NIGHTS = 30.
List<LocalDate> nights()
Every date from checkIn inclusive to checkOut exclusive, ascending. A 10th→13th range yields [10th, 11th, 12th].
int nightCount()
nights().size(); equals ChronoUnit.DAYS.between(checkIn, checkOut).
boolean overlaps(DateRange other)
Half-open interval semantics: a range ending on the day another begins does not overlap (guest A checks out, guest B checks in, same day, same room — legal).
boolean contains(LocalDate date)
True for checkIn <= date < checkOut.
boolean isBefore(LocalDate reference)
checkOut <= reference. Used for CONFIRMED → COMPLETED.

Checkout-exclusive semantics are the single most important rule in this class. A hotel night is the night you sleep there; checkout day is not one. Getting this wrong produces off-by-one overbooking that no other test will catch. State it in the Javadoc.
nights() must be the only place in the codebase that expands a range into dates.
2.3 Money
public record Money(BigDecimal amount, String currency)

Compact constructor: rejects null; rejects negative; normalises scale to 2 with RoundingMode.HALF_EVEN; currency must be a 3-letter uppercase ISO code.
static Money of(String amount, String currency), static Money inr(String amount), static Money zeroInr().
add, subtract, multiply(int), percentage(BigDecimal), isZero(), isGreaterThan(Money), isLessThan(Money).
Every binary operation throws CurrencyMismatchException on differing currencies.
subtract producing a negative throws — negative money is meaningless here. Refund direction is modelled by LedgerEntry.direction in a later phase, not by sign.
equals must treat 10.00 and 10.0 as equal. BigDecimal.equals does not — compare via compareTo on the normalised value, and write a test pinning this.
No double or float anywhere in this class.
2.4 UnitCount and GuestCount
public record UnitCount(int value)      // rooms
public record GuestCount(int adults, int children)

UnitCount: >= 1; <= MAX_UNITS_PER_BOOKING = 10 (a domain rule, stated in Javadoc, not read from config — domain has no config access). static of(int), static one().
GuestCount: adults >= 1, children >= 0, total(). A booking with zero adults is invalid.
These are separate types precisely because "2" as rooms and "2" as guests are different things, and a swapped argument must not compile.
2.5 Location
public record Location(String city, String locality, BigDecimal latitude, BigDecimal longitude)

city required non-blank; locality optional; lat/long optional but must both be present or both absent, and within valid ranges when present.
String normalisedCity() — trimmed, lowercased, internal whitespace collapsed. Used for search matching so "Bengaluru", "bengaluru" and " Bengaluru " match. The original casing is preserved for display.
2.6 InventoryKey — must be Comparable
public record InventoryKey(RoomTypeId roomTypeId, LocalDate stayDate)
        implements Comparable<InventoryKey>

compareTo orders by roomTypeId.value() then stayDate.
Why this matters: Phase 3 reserves N nights inside one transaction, and each conditional UPDATE holds a DB row lock until commit. Two multi-night bookings acquiring nights in opposite order deadlock. Total ordering on this key is the mechanism that prevents it. Comparable is therefore a correctness requirement, not a convenience — say so in the Javadoc so nobody removes it later.
Also provide static List<InventoryKey> orderedFor(RoomTypeId id, DateRange range) returning keys sorted, so callers cannot accidentally iterate unsorted.

* Add REVERSED to the enum. It was omitted from the list above deliberately so you notice: the transition table references it, so the enum needs it, and it is terminal.
BookingStateMachine API:
boolean canTransition(BookingState from, BookingState to);
void assertCanTransition(BookingState from, BookingState to);  // throws
boolean isTerminal(BookingState state);
Set<BookingState> allowedFrom(BookingState state);

Two required behaviours:
Same-state transition is a permitted no-op, not an error. canTransition(CONFIRMED, CONFIRMED) returns true and does nothing. Reason: payment gateways retry webhooks, and a duplicate PAYMENT_SUCCESS must not throw. This is idempotency at the state-machine level.
assertCanTransition throws InvalidStateTransitionException naming both states.
The table must be total — every enum constant has an entry, terminal states mapping to an empty set. A missing entry must not fall through to "allowed".
2.8 Booking and BookingLineItem
public final class Booking {
    private final BookingId id;
    private final GuestId guestId;          // reference only — NEVER inline guest PII
    private final PropertyId propertyId;
    private final RoomTypeId roomTypeId;
    private final DateRange dateRange;
    private final UnitCount units;
    private final GuestCount guestCount;
    private final List<BookingLineItem> lineItems;   // unmodifiable
    private final Money totalAmount;
    private final Instant createdAt;
    private final Instant holdExpiresAt;
    private BookingState state;
    private long version;
}

public record BookingLineItem(
    LocalDate stayDate,
    UnitCount units,
    Money pricePerUnit,      // SNAPSHOT — never recomputed
    Money lineTotal          // = pricePerUnit × units
)

Invariants enforced on construction:
lineItems has exactly one entry per date in dateRange.nights(), no duplicates, no gaps. Violation throws.
Every line item's units equals the booking's units.
lineTotal == pricePerUnit × units for each item.
totalAmount == sum(lineTotals).
lineItems exposed as an unmodifiable list; the class is otherwise immutable except state and version.
guestId is a reference and Booking must contain no guest name, email, phone or address. This is not tidiness: a later phase must be able to erase a guest's personal data while leaving the booking and its financial trail intact. Personal data inside Booking would make that impossible. Put this in the class Javadoc.
Methods:
void transitionTo(BookingState next, BookingStateMachine fsm) — delegates the check to the FSM, then assigns. No transition logic inside Booking.
boolean isHoldExpired(Instant now) — now is a parameter. Never call Instant.now().
boolean isPastCheckout(LocalDate propertyLocalToday).
Use a builder (Booking.builder()) — too many fields for a constructor. Hand-write it or use Lombok @Builder, but not @ToString (see §4).
2.9 Property-local date resolution
package com.umesh.hotelbooking.domain.port;

public interface PropertyClock {
    LocalDate todayAt(ZoneId zone);
    Instant now();
}

Plus infrastructure-side SystemPropertyClock wrapping an injected java.time.Clock, and a test FixedPropertyClock.
Why: a UTC server calling LocalDate.now() returns the wrong calendar day for an IST property near midnight, silently corrupting availability lookups and checkout comparisons. Every "what is today" question must be answered relative to the property's zone.

3. Tests — required, with the specific assertions
Plain JUnit 5 + AssertJ. No Spring context in this phase. Every test must run in milliseconds.
DateRangeTest
nights() for 10th→13th returns exactly [10th, 11th, 12th] — three entries, checkout excluded.
nights() for a one-night stay returns one entry.
checkOut == checkIn throws; checkOut < checkIn throws.
Stay exceeding 30 nights throws.
overlaps is false when one range's checkOut equals another's checkIn — the same-day turnover case. This is the assertion most likely to be got wrong.
overlaps is true for partial overlap, full containment, and identical ranges.
nightCount() agrees with nights().size() across a month boundary and a leap day.
MoneyTest
Money.inr("10.00").equals(Money.inr("10.0")) is true (the BigDecimal.equals trap).
Scale normalises to 2; 10.005 rounds half-even.
Negative construction throws.
add/subtract across differing currencies throws CurrencyMismatchException.
subtract yielding negative throws.
multiply(3) on a per-night rate gives the expected total.
BookingStateMachineTest
Every allowed transition in the §2.7 table returns true — table-driven, not one test each.
Every disallowed pair throws — iterate the full cartesian product of states and assert anything not in the table is rejected. This is what makes the machine total.
Same-state transition is permitted for all states.
Terminal states have an empty allowed set and reject everything except themselves.
Every enum constant has a table entry (guards against a future state being added and silently defaulting to permissive).
BookingTest
Line items exactly match dateRange.nights(); a missing night throws; a duplicate throws.
totalAmount mismatching the line-item sum throws.
Per-night prices differing across a weekend produce the correct total.
getLineItems() is unmodifiable — mutation attempt throws.
isHoldExpired with an injected Instant behaves at, before and after the boundary.
Multi-unit: 2 units × 3 nights produces 3 line items each with units == 2, and totalAmount == sum(pricePerUnit × 2).
InventoryKeyTest
orderedFor returns keys in ascending date order given an unsorted input range.
compareTo orders by roomTypeId then date; sorting a shuffled list is deterministic.
PropertyLocalDateTest
Fixed clock at 2026-09-07T18:40:00Z; todayAt(Asia/Kolkata) returns 2026-09-08 (IST is UTC+5:30, so it is already the next day locally). Assert the UTC answer differs. This test is the guard against the classic timezone bug.

4. Coding rules — non-negotiable
No framework types in domain. No org.springframework.*, no jakarta.persistence.*, no Jackson annotations. If you reach for one, the design is wrong — stop and ask.
No now() in domain. No Instant.now(), LocalDate.now(), System.currentTimeMillis(). Time arrives as a parameter or via PropertyClock.
No Lombok @Data or @ToString on anything holding personal or payment data. Hand-write toString() on those types, and omit or mask the sensitive fields. @Builder, @Getter and @RequiredArgsConstructor are fine elsewhere. Rationale: an accidental log.info("{}", booking) is the most common personal-data leak there is, and a generated toString guarantees it.
Records for value objects, classes for entities. Value objects are immutable and compared by value; entities have identity and (limited) mutable state.
Validate in the compact constructor. An invalid value object must be unconstructable — not validated later by a caller.
No double/float for money. BigDecimal only.
Javadoc on every public type, one or two sentences: what it is and any non-obvious rule. Where this spec gives a rationale (checkout-exclusive nights, Comparable on InventoryKey, guestId as reference-only), put that rationale in the Javadoc — the next person to touch it needs to know why, or they will remove it.
Small commits, one per §2 subsection, message describing what and why.
