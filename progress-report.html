What's been built, phase by phase

Each phase was built to work fully before the next one started — the same way you'd finish a hotel's foundation before framing the walls. The diamond marker is a one-time detour: a design decision that got reconsidered and simplified partway through, not a numbered phase.

0

Setting up the workshop

Before laying a single brick, a construction crew sets up scaffolding and orders its tools. This was the software version of that.

  • Generated a brand-new backend project in Java, using Spring Boot (a widely-used toolkit for building backend systems) — picking the newest stable version of each.
  • Set up a small, built-in database (H2) so the whole project runs on a laptop with nothing extra to install — no separate database software needed to try it out.
  • Configured the build so that any code warning is treated as a hard error, catching sloppy mistakes immediately instead of letting them pile up unnoticed.
  • Organized the codebase into clear folders (entities, services, controllers, and so on) before any actual hotel logic was written.
  • Put the whole project under version control (a system that keeps a permanent, undoable history of every change) and made the first save point.
Caught early

Before writing any hotel logic, a payment safety-net library was test-installed to check it would actually work with the chosen versions — and it turned out not to be available yet for this newer setup. Finding that on day one, instead of getting stuck with it mid-project, meant Phase 4 could plan around it from the start.

Teaching the computer what a "booking" is

Before you can run a hotel, everyone has to agree on definitions: what counts as a booking, what stages it passes through, and which stage-changes are even allowed.

  • Defined the core building blocks: a Booking, its nightly line items (one row per night stayed, since a 3-night stay can have three different nightly rates), and every price and date rule that protects them.
  • Built a strict rulebook — called a state machine — of exactly which booking status can move to which other status. A booking can go from "awaiting payment" to "confirmed," for example, but can never jump straight from "confirmed" back to "awaiting payment."
  • Wrote 48 automated checks proving every one of those rules genuinely holds, including every single disallowed combination, not just the allowed ones.
  • Built the custom error types the system uses to explain precisely what went wrong — "this date range is invalid" reads very differently from "this booking is already cancelled," and callers need to tell them apart.
◆

A mid-course simplification

Like a building renovation partway through construction, done before more floors were added on top.

  • The original plan kept two separate descriptions of a Booking — one for pure business rules, one for actually saving it to the database. It's a well-known professional pattern, but it adds real complexity.
  • On request, this was simplified to one description per concept, using a popular shortcut tool (Lombok) that writes a lot of the repetitive code automatically.
  • Introduced the "two-ID" pattern used across the industry: every important record (a Booking, a Property, a Payment) now has a private internal database number nobody ever sees, plus a separate public random ID that the app or website actually uses — the same idea as your bank account number staying internal while a reference number gets printed on your receipt.
2

Hotels, room types, and nightly prices

This is where real hotels "move in" — their room types, how many rooms of each exist, and what each one costs on any given night.

  • Built the ownership chain: Owner → Hotel Group → Property (one hotel) → Room Type → nightly availability. An independently-owned hotel is automatically treated as "a group of exactly one," so there's no special-case code anywhere asking "is this a chain or not?"
  • Every room-type-and-night combination gets its own row — like a giant spreadsheet: Deluxe King, 10 Sept, 12 total rooms, 3 already booked, ₹8,000/night — created 90 days ahead automatically the moment a hotel signs up.
  • Added a rule enforced by the database itself, not just by careful code, making it mathematically impossible for booked rooms to ever exceed the rooms that exist for a given night.
  • Built three interchangeable pricing rules a hotel can choose from: a flat nightly rate, a weekend price bump, or custom seasonal pricing (a Diwali surge, say) — and an admin can re-run pricing on already-created nights without touching a booking that's already been made.
  • Loaded a realistic demo dataset: 11 hotels across 6 Indian cities, including one 3-hotel chain and eight independents, so there's real-feeling data to explore immediately.
Real trap avoided

Made sure "what day is it right now" is always calculated using the hotel's own local time zone, never the computer server's. Otherwise a hotel in Bengaluru could show the wrong day's rooms as available right around midnight.

3

The booking engine

The single hardest problem in any booking system: what happens when two guests try to grab the very last room at the exact same instant?

  • Built a one-step, unsplittable database instruction that checks availability and reserves the room at the same time — there's no tiny gap in between where two guests could both slip through and both "win" the same last room.
  • Multi-night bookings are all-or-nothing: if a 3-night stay is bookable except for night 2, nothing gets booked at all, rather than confirming a broken partial reservation.
  • Solved a subtle trap called deadlock, where two bookings could each get stuck forever waiting on the other, by always reserving nights in a fixed, predictable order.
  • Added a background "sweeper" that automatically frees up rooms held by guests who never finished paying within 15 minutes, and marks finished stays as complete once checkout has passed.
  • Proved all of this with 6 dedicated stress tests, including one that fires 20 booking attempts at the exact same last room at the exact same moment and checks that exactly one succeeds — every single time.
Proof, not just hope

To make sure the stress tests weren't passing by accident, the safety code was deliberately broken on purpose for a moment — the tests failed immediately, exactly as they should have — then it was fixed back. A test that can't catch a real break isn't proving anything.

4

Handling payments (and everything that can go wrong)

Payment software has to face an uncomfortable truth: sometimes an attempt times out and you genuinely don't know whether the money moved. That's neither "it worked" nor "it failed" — it needs its own honest category.

  • Built simulated payment methods (Card, UPI, Wallet) standing in for real banks — this is a learning project, so no real money or real bank is ever touched.
  • Built a "circuit breaker" by hand: if the payment service starts failing repeatedly, the system automatically stops calling it for a short cooldown, the same idea as a household electrical breaker tripping to prevent damage, then quietly tests the waters again afterward.
  • Added automatic retries for brief blips, but never for a payment that's genuinely declined or unresolved — retrying a real failure risks charging a guest twice.
  • Created a distinct "payment status unknown" state for timeouts, with a background process that keeps checking back on it on a gradually slowing schedule (30 seconds, then a minute, then two) until it resolves on its own or gets handed to a human admin to review.
  • Built in protection against a guest accidentally clicking "Pay" twice: the second click safely returns the exact same result as the first, instead of charging twice.
Real bug found

Discovered, by actually trying it, that retrying payment on an already-declined booking produced a confusing internal error instead of a clear "you'll need to make a new booking" message — fixed to fail clearly and helpfully instead.

5

Cancellations, refunds, and the money trail

Hotels need cancellation policies — full refund if you cancel early enough, nothing last-minute — and, just as importantly, a permanent record of every rupee that ever moved, the same principle as a bank statement that can never have a line secretly edited afterward.

  • Built three interchangeable cancellation policies a hotel chain can choose from: full refund with 48+ hours' notice, half back with 24+ hours' notice, or free cancellation right up until check-in.
  • Built an append-only financial ledger: every charge, refund, or correction becomes a new permanent entry, and existing entries are never edited or deleted — mistakes get fixed by adding a new balancing entry, never by rewriting history.
  • Added a hard mathematical safety rule: the system can never refund or reverse more money than was actually charged for a booking, checked before anything gets written.
  • Modelled "reversal" as its own concept, separate from a normal refund, for the rare case where a payment succeeds very late — after its hold already expired and the room was resold to someone else. Both the original charge and its undo get permanently recorded, so the books always balance.
Real bug found

By actually running the "payment succeeds very late" scenario start to finish, not just reading the code, discovered the system was trying to reverse a charge before it had ever recorded that the charge happened — like trying to void a receipt that was never printed. Fixed so the charge is always logged first.

A few terms, explained simply

The handful of technical words above that couldn't be avoided — explained the way they actually work here.

API
The fixed "menu" of requests a website or app is allowed to make to this backend — like the set list of things you can ask for at a hotel front desk.
Database
The permanent filing cabinet where every booking, hotel, and payment record lives, even after the computer restarts.
Concurrency
What happens when more than one person tries to do the same thing — like book the same room — at the exact same moment.
Circuit breaker
A safety switch that stops repeatedly calling a struggling service, the same idea as a home electrical breaker tripping to prevent damage.
Ledger
A permanent log of every financial transaction that only ever gets new entries added — never edited or deleted.
Idempotency
Doing something twice by accident, like double-clicking "Pay," has the exact same effect as doing it once.
State machine
A strict rulebook defining exactly which status changes are allowed — and which ones are not.
Automated test
A small robot check that runs the code and confirms it behaves correctly, in milliseconds, without a human doing it by hand.
